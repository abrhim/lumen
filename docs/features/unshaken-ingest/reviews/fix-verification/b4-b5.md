## B4: scrubSecrets known-key fallback is dead code — VERIFIED

Mechanism: `makeScrubber(apiKey)` (util.mjs:39-41) closes over the live key
and passes it as `extraSecrets` on every call — this **bypasses**, rather
than repairs, the dead `process.env.DEEPGRAM_API_KEY` fallback inside
`scrubSecrets` (util.mjs:12), which CSEC-3's adversarial repro already
confirmed nothing sets. bugs.md records the alternative (setting the env var)
as REJECTED — it would regress 47bf9d2. That fallback is *expected* to stay
dead; the fix routes around it.

### Executed repro
`makeScrubber('FAKEKEY123abcXYZ')` against 3 message shapes, plus a control:

- **B4a** — Deepgram JSON-error-body shape exactly matching index.mjs:181
  (`` `Deepgram ${res.status}: ${scrub(body.slice(0,300))}` ``), key with
  **no** `"Token "` prefix → redacted.
  Output: `Deepgram 400: {"err":"Invalid credentials, key=*** rejected"}`
- **B4b** — same shape *with* `"Token "` prefix → also redacted (double
  coverage: regex + extraSecrets).
- **B4c** — key mid-sentence, no delimiter word nearby → still redacted.
  B4a/B4c deliberately avoid the `"Token "` prefix so a pass can only be
  explained by the `extraSecrets` loop (the actual B4 fix), not the
  pre-existing generic regex.
- **B4d (control)** — bare `scrubSecrets(msg)`, no `extraSecrets`, no
  `process.env.DEEPGRAM_API_KEY` set → key **leaks** (assertion expects the
  leak). Confirms the internal fallback is still genuinely dead — the
  intended shape, not a regression.

All 4 passed as expected (3 redacted / 1 confirmed-still-dead-by-design).

## B5: Non-atomic deepgram.json write — VERIFIED (core); RESIDUAL (adjacent artifact)

Mechanism: `writeArtifactAtomic(path, data, {writeFileSync, renameSync})`
(util.mjs:44-48) writes `${path}.tmp` then `renameSync`s over the final
path. index.mjs:186 — `writeArtifactAtomic(artifact, JSON.stringify(dg),
{writeFileSync, renameSync})` — is the transcribe stage's only write of the
deepgram artifact. `grep -n "writeFileSync\|renameSync" index.mjs` finds
exactly two raw `writeFileSync` occurrences in the whole file: line 98
(episodes.json — see residual below) and line 186 (inside the
`writeArtifactAtomic` call). No other write of a `.deepgram.json` path
exists anywhere in the runner.

### Executed repro (real fs, `mkdtempSync` temp dir, no mocks)

- **B5a — success path.** Real `writeFileSync`/`renameSync` through
  `writeArtifactAtomic`: final file exists with byte-identical content,
  `${final}.tmp` does not exist afterward. PASS.
- **B5b — crash-between-write-and-rename.** Called
  `writeFileSync(`${final}.tmp`, data)` directly and skipped `renameSync`
  (mimics a kill mid-write). Result: `.tmp` orphaned on disk, **final path
  stays absent**. Re-executed the *exact* guard index.mjs:148 uses
  (`existsSync(artifact)`) against this state → `false` — `transcribeEpisode`
  would skip the `try { JSON.parse(...) }` block entirely and fall straight
  through to a fresh Deepgram request; the crash is invisible to the cache
  logic rather than merely "handled." Then confirmed the orphaned `.tmp` is
  inert: the next `writeArtifactAtomic` call on the same path overwrites it
  (writeFileSync truncates the existing tmp) and completes atomically, `.tmp`
  gone again. PASS.
- **B5c — corrupt-final-file self-heal** (belt-and-suspenders, in case
  corruption reaches the final path by any other route). Wrote truncated
  JSON directly to the final path, then executed index.mjs:148-156's exact
  logic (`existsSync`→true, `JSON.parse`+`validateUtterances` in `try`,
  `catch` sets the stale reason) using the real `validateUtterances` import.
  Confirmed: parse throws, is caught, cache-hit is `null`, stale-reason is a
  JSON parse error — matches the `transcribe_stale` log path, which falls
  through to re-transcribe instead of crashing the run. Reproduces the
  "truncated-JSON self-heal" CSEC-4's adversarial pass asserted. PASS.

**B5 core verdict (deepgram.json): VERIFIED.** The final path is now only
ever fully-absent, fully-old, or fully-new — never partial — and the
independent self-heal catch still works for corruption from any other
source.

### Residual hunt: episodes.json (discover stage)

index.mjs:98 writes `episodes.json` via a **bare `writeFileSync`**, not
`writeArtifactAtomic` (the other of the two writeFileSync sites found above).
The read side is unguarded too — index.mjs:74:

```js
const cached = JSON.parse(readFileSync(artifact, 'utf8'));
```

has **no try/catch**, unlike `transcribeEpisode`'s equivalent cache-check
(148-156), which wraps its parse and self-heals on failure. plan.md:110
documents the intended contract as "exists AND passes a validity check," but
a parse failure never reaches `isValidEpisodesArtifact` — it throws past it.

Executed repro: wrote a truncated JSON string directly to a temp
`episodes.json` (simulating a crash mid-`writeFileSync`, which for this
artifact lands directly on the real filename — there is no tmp-staging to
absorb it), then ran index.mjs:74's exact expression against it.

- `JSON.parse(readFileSync(artifact, 'utf8'))` **throws** — the corruption
  scenario is real and reachable.
- The throw is not caught in `discover()`; it propagates to `main()`'s outer
  try/catch (index.mjs:266-368), which does catch it, scrubs it (control-
  checked: still the baked B4 scrubber at that site), and exits **1**
  (fatal) — this fails loud/safe, not silent, and leaks no secret.
- Nothing clears or rewrites the corrupt file on that path — the
  `writeFileSync` that would refresh it (line 98) is never reached, since the
  throw happens first. Re-ran the same parse against the same file a second
  time (simulating the next invocation without `--refresh`) → **throws
  again**. The pipeline is wedged for this show on every subsequent run until
  an operator deletes the file or passes `--refresh`.
- Control check: the *other* half of discover's validity gate — well-formed
  JSON with a wrong semantic shape (e.g. wrong episode count) — correctly
  returns `false` from `isValidEpisodesArtifact` and is handled gracefully.
  Only the raw-parse step is unguarded; H10/CON-8's validity check itself is
  fine.

This is the same crash-mid-write failure family B5 was scoped to fix, left
open on a second JSON artifact. It was not in scope for CSEC-1/CSEC-4, both
of which were scoped explicitly to "deepgram.json" + "m4a" (m4a is covered
separately by yt-dlp's own `.part`+rename per H3, unrelated to this
pipeline's own fs writes). Impact is narrower than the original B5
(episodes.json is a small, fast, once-per-run write vs. deepgram.json's
long upload/transcribe window), and the failure mode is loud/safe rather
than silent-corruption or secret-leaking — but it's a genuine, currently
un-mitigated gap, and the same file already demonstrates the correct pattern
(transcribe's local try/catch self-heal) immediately next to the unguarded
one.

**B5 residual verdict: RESIDUAL** — `episodes.json` write (index.mjs:98) is
non-atomic and its read-side parse (index.mjs:74) is unguarded, unlike the
now-fixed deepgram.json path. Not filed as a new bugs.md entry by this pass
(outside a fix-verification agent's scope); flagging for triage.
