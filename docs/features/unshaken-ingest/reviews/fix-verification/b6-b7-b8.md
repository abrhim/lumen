created a real (never-staged, fully cleaned up after) `data/podcasts/hypothetical/`
with `episodes.json`, `fakeaudio.m4a`, and `run-999-999.log`, then ran
`git add --dry-run -v data/podcasts/hypothetical/`:


are silently excluded, matching `git status --porcelain --ignored=matching`
(`!! fakeaudio.m4a`, `!! run-999-999.log`, manifest not marked `!!`). This is
the operative, real-world test for "committable" and it passes cleanly.

**Methodology note (not a bug):** `git check-ignore -v` on
`data/podcasts/hypothetical/episodes.json` reports exit 0 (showing the
negation pattern as the match) — this looks like a fail against "expect exit
1" at first glance. Isolated the cause: `-v` changes what the exit code
means. Without `-v`, exit code correctly reflects net ignore status (0 =
ignored, 1 = re-included/not-ignored) — confirmed by running the identical
path with and without `-v` side by side. The re-trigger instructions specify
plain `git check-ignore` (no `-v`), which is exactly what returns the
expected exit 1. Recorded here so a future re-run with `-v` added for
debugging doesn't get misread as a regression.

## B8: Rest-fetches blocked behind probe chain (Amendment-1's cheap half) — VERIFIED (structural, as scoped)

plan.md:183-184 records this bug as "repro-deferred (structural — verify via
next backfill's mtime overlap)" — the fix-round itself anticipated this stays
a structural/traced verification rather than a fresh executed one, since a
true cold-cache demonstration means re-fetching+re-transcribing real episodes
(real Deepgram cost) and all 10 unshaken episodes are already fully cached.
Treated accordingly below: code trace is the primary evidence, with a
same-commit executed log used only as corroboration, and both are clearly
labeled traced vs. executed.

### Structural trace (index.mjs)

```
302   // B8: rest FETCHES start immediately, concurrent with the probe chain;
303   // the REL-3 gate only serializes TRANSCRIPTION behind the probe.
304   log('probe_start', { episode: probe.id, duration_s: probe.durationS });
305   const restFetches = runPool(
306       rest.map((ep) => async () => {
307           await fetchEpisode(ep, dir, opts);
308           return ep;
309       }),
310       show.pools.fetch,
311   );
312
313   let probeFailed = false;
314   try {
315       await fetchEpisode(probe, dir, opts);              // probe fetch
316       if (opts.stage !== 'fetch') await transcribeAndLoad(probe);  // probe transcribe+load
317       results.ok.push(probe.id);
...
324   const fetchResults = await restFetches;                // rest fetches awaited HERE
```

`runPool(...)` is called at line 305 — textually before line 315's
`await fetchEpisode(probe, ...)` — and it is *not itself* awaited until line
324, after the probe's full fetch-then-transcribe-then-load chain (315-317)
has already run to completion inside the `try`. That satisfies "runPool must
START before awaiting the probe chain" as a line-order fact, but the
stronger claim is that it starts *doing real work* before then too:
`runPool` (util.mjs:66-82) is an `async function` whose body, up to its own
first suspend point, runs synchronously the instant it's called — it builds
`results`, then `Array.from({length: min(limit, n)}, worker)` at line 79
*synchronously invokes* `worker()` for each of `limit` pool slots, and each
`worker()` synchronously dequeues and *calls* (not just schedules)
`taskFns[i]()` — i.e. `fetchEpisode(ep, ...)` for up to `show.pools.fetch`
(=2) rest episodes actually starts executing (cache check, or the real
`yt-dlp` `execFile` call) before `runPool()`'s own first `await
Promise.all(workers)` returns control to `main()`. So by the time `main()`
reaches line 315, up to 2 rest-episode fetches are already in flight, not
merely "queued."

REL-3 gate: rest-episode *transcription* runs only inside the second pool at
340-347 (`runPool(fetched.map(ep => async () => { await
transcribeAndLoad(ep); ... }), show.pools.transcribe)`), built from
`fetched` — which is only populated after `const fetchResults = await
restFetches` (324) resolves. That pool call is never even reached until
after: (a) the probe's own `transcribeAndLoad` (line 316) has been awaited
to completion inside the earlier `try`, and (b) `restFetches` has resolved.
If the probe fails, line 335's `if (probeFailed ...) return finish(2)`
returns before line 340 is reached at all — so the rest-transcribe pool
never starts if the probe never proved the upload mechanics. Both halves of
"rest fetches proceed underneath, but transcription stays gated on the
probe" hold structurally.

### Runtime recipe for full cold-cache verification (documented, not executed here — matches plan.md:184's deferral)

Next time real network fetch/transcribe work is unavoidable — onboarding a
second show (empty `data/podcasts/<show>/`) or the weekly unshaken re-run

grep the event stream for:
