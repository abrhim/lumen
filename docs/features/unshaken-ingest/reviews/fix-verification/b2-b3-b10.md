## B2 — Collection upsert reverts Phase B's public flip — **VERIFIED**

**The fix (`bcec780`, `load.mjs`):** the `ON CONFLICT` clause dropped
`public = EXCLUDED.public`:

```diff
 ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name, description = EXCLUDED.description,
   tier = EXCLUDED.tier, category = EXCLUDED.category, provenance = EXCLUDED.provenance,
-  license = EXCLUDED.license, storage = EXCLUDED.storage, public = EXCLUDED.public`,
+  license = EXCLUDED.license, storage = EXCLUDED.storage`,
```

**Live re-trigger of the exact Phase-B-flip scenario** (script `05-b2-transaction.mjs`),
inside one transaction:

1. Baseline read: `{"id":"unshaken","public":false}`
2. `UPDATE lumen.collections SET public = true WHERE id = 'unshaken'` (simulates Phase B) → confirmed `public: true`
3. Called the real `buildLoadPlan(...)` (imported, not hand-copied), extracted
   `plan.statements.find(s => s.text.includes('INSERT INTO lumen.collections'))`
   — i.e. the actual statement the loader would run on a routine weekly
   re-run — and executed it with its own `.values`, mapped through the
   identical `v => typeof v === 'object' ? JSON.stringify(v) : v` rule
   `loadEpisode` uses:

   ```sql
   INSERT INTO lumen.collections (id, name, description, tier, category, provenance, license, storage, public)
   VALUES ($1, $2, $3, $4, $5, $6, $7, $8, $9)
   ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name, description = EXCLUDED.description,
     tier = EXCLUDED.tier, category = EXCLUDED.category, provenance = EXCLUDED.provenance,
     license = EXCLUDED.license, storage = EXCLUDED.storage
   ```
   values: `["unshaken","Unshaken","Come Follow Me deep-dive scripture study with Jared Halverson (weekly, verse by verse)","app","podcast","youtube","embedded playback; transcript indexed for navigation","link",false]`
   (note `values[8] = false` — this is exactly the landmine: the INSERT side
   still seeds `false`, so if `public` were still in the SET list this
   would revert the flip)
4. Post-upsert read, same transaction: **`public: true`** — the flip survived.
5. `ROLLBACK` (sentinel throw).

Result: `public` was `true` after the real upsert statement ran with its
real values while the corresponding `EXCLUDED.public` was `false` — proves
the ON CONFLICT clause genuinely never touches the column, not just that the
SQL text looks right. Post-rollback state confirmed identical to baseline
(`public: false`).

**Verdict: VERIFIED.**

## B3 — Whole-book search block-label renders "Joshua 1" — **VERIFIED**

**The fix (`bcec780`, `load.mjs`):** replaced an inline label expression with
`blockLabel()`:

```diff
+function blockLabel(spans) {
+	return spans
+		.map((s) => {
+			if (s.end === null || s.end === undefined) return s.book;
+			if (s.end === s.start) return `${s.book} ${s.start}`;
+			return `${s.book} ${s.start}-${s.end}`;
+		})
+		.join(' · ');
+}
...
-			episode.spans.map((s) => `${s.book} ${s.start}${s.end && s.end !== s.start ? `-${s.end}` : ''}`).join(' · '),
+			blockLabel(episode.spans),
```
The old expression for a whole-book span (`start:1, end:null`) evaluates
`s.end && ...` → `null` is falsy → no `-${end}` suffix → `"Joshua 1"`. This
is the literal bug mechanism.

### 1. Fresh execution of `buildLoadPlan` for all 3 span shapes (+ multi)

Script `02-b3-unit.mjs` extracts `plan.statements.find(s =>
s.text.includes('INSERT INTO lumen.search_index')).values[4]` — the actual
`blockLabel()` output the live loader would write into the C-weight tsvector
today:

| shape | spans | expected | got | pass |
|---|---|---|---|---|
| whole | `Joshua {1,null}` | `Joshua` | `Joshua` | PASS |
| single | `Exodus {19,19}` | `Exodus 19` | `Exodus 19` | PASS |
| range | `Exodus {19,34}` | `Exodus 19-34` | `Exodus 19-34` | PASS |
| multi (whole+range) | `Ruth{1,null}·1 Samuel{1,7}` | `Ruth · 1 Samuel 1-7` | `Ruth · 1 Samuel 1-7` | PASS |

### 2. Live rows — the three actual whole-book episodes

`search_index` stores no raw label column; the label only exists baked into
`tsv` at weight C, so verification is a `tsquery` match, per instructions.
Sanity check first (script `03-b3-live-tsquery.mjs`), to prove the test
methodology *can* detect the bug if it were present:

```
to_tsvector('english', 'Joshua 1') → '1':2 'joshua':1     -- a stray "1" WOULD tokenize and be findable
to_tsquery('english', '1')         → '1'                   -- and IS a valid, matchable query
```

Then, against the live rows:

| ref_id | book | `tsv @@ 'book'` | `tsv @@ 'book:C'` | `tsv @@ '1'` (bare digit anywhere) | `tsv @@ '1:C'` |
|---|---|---|---|---|---|
| unshaken-8SvK7L87o1A | joshua | true | true | **false** | false |
| unshaken-ki0bTvQsaCo | numbers | true | true | **false** | false |
| unshaken-yAQlljeet-0 | leviticus | true | true | **false** | false |

Raw `tsv::text` for corroboration:
```
unshaken-8SvK7L87o1A: 'book':5A 'choos':8A,12B 'come':1A 'day':11A,15B 'follow':2A 'joshua':7A,16C
unshaken-ki0bTvQsaCo: 'book':5A 'come':1A 'follow':2A 'live':10A,13B 'look':8A,11B 'number':7A,14C
unshaken-yAQlljeet-0: 'book':5A 'come':1A 'follow':2A 'holi':8A,12B 'leviticus':7A,16C 'lord':11A,15B
```
Book name carries a weight-C occurrence (position 16A,7A / 14A,7A / 16A,7A —
i.e. present twice: once from the title at weight A, once from the block
label at weight C), and **no digit lexeme exists anywhere in any of the
three rows** — the query still finds the book, with no false chapter-1
impression.

**Verdict: VERIFIED.**

**Observation (not a B3 residual, flagged for awareness):** `blockLabel`'s
`end === null` branch returns the bare book name regardless of `start`. The
cross-book episode `unshaken-O3SiM9Yi940` ("1 Samuel 17 - 2 Samuel 10 -
...") produces span `{book:'1 Samuel', start:17, end:null}` for its first
half (parseTitle's "run to end of book" encoding, confirmed live: label
component renders as bare `"1 Samuel"`, dropping the "starts at 17"
specificity — verified in the live tsv: weight-C lexemes decode to `1
samuel 2 samuel 1 -10`, i.e. `"1 Samuel · 2 Samuel 1-10"`, no `17` anywhere
at weight C). This does **not** reproduce the false-chapter-1 pattern (it
omits the chapter rather than asserting a wrong one) and B3's own scope was
explicitly "3 of 10" (Joshua/Numbers/Leviticus only) plus exactly 3 named
shapes (whole/single/range) — this is an unaddressed 4th shape
(partial-book-to-end), not a regression of the fix. Not raising as a bug;
noting for the retro/future filing.
