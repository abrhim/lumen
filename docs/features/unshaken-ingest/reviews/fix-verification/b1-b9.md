## B1: Partial-failure exit code masked by tee invocation — VERIFIED

Mechanism: `makeRunLogPath(dir, {now, pid})` (util.mjs:52-54) returns
`${dir}/run-${now}-${pid}.log`; `main()` calls it once per invocation
(index.mjs:251) and opens it with `createWriteStream` — no shared filename,
no tee in the runner's own invocation contract (top-of-file comment,
index.mjs:2, documents bare invocation only).

### Executed repro 1 — two sequential invocations, distinct files, no cross-contamination

```

$ node --import tsx scripts/ingest-podcast/index.mjs --show=unshaken --stage=discover --dry-run
```

Filenames differ in both `now` and `pid` components — genuinely distinct

## Residual hunt

### Asked: does `finish()` flush the log stream before exit? (no truncated tail)

Checked for all three of my successful dry-runs (`finish(0)` path,
index.mjs:370-374, which does `await sql.end(); await new
Promise((r) => logSink.end(r)); process.exit(code);`):

| Run | stdout lines | file lines | `diff` |
|---|---|---|---|
| discover dry-run #1 | 2 | 2 | clean |
| discover dry-run #2 | 2 | 2 | clean |
| full dry-run | 37 | 37 | clean, trailing `}\n` present (checked with `xxd`) |

No truncation in any case — `logSink.end(callback)` genuinely waits for the
stream to flush before `finish()` calls `process.exit()`. **Clean.**

### Found (not asked, adjacent): `fatal()` does NOT flush before exit — real data loss, not just theoretical

Reading `fatal()` (index.mjs:57-67) against `finish()` shows an asymmetry:
`finish()` awaits `logSink.end()`; `fatal()` fires `logSink?.write(...)`
(fire-and-forget) then calls `process.exit(1)` synchronously, with **no**
`await`/`setImmediate`/callback in between.

Two of `fatal()`'s four call sites are safe by construction — args-parse
failure (index.mjs:244) and unknown `--show` (index.mjs:247) both fire
*before* `logSink` exists, so there's no file to lose (confirmed above: no
log file was created for the bad-`--show` repro). But the other two —
missing `DATABASE_URL` (index.mjs:259) and missing `DEEPGRAM_API_KEY`
(index.mjs:261) — fire *after* `logSink` is created (index.mjs:252) and
after `run_start` has already been queued to it, with only synchronous code
(`createRequire`, `require('postgres')`, `readFileSync`, two regex matches)
in between.

I built an isolated repro (not touching the real repo's `.env`/DB) that
copies this exact shape — `createWriteStream` → `log('run_start', …)` →
`require()` a real heavy dependency (the actual `postgres` package from this
repo's `node_modules`, to match wall-clock timing) → `readFileSync` a
fake `.env` missing `DATABASE_URL` → `fatal()`:
`/private/tmp/claude-501/-Users-abram-code-lumen/2126f42a-c5d8-4692-811e-192bc0538165/scratchpad/b1b9/flush-repro2.mjs`.
Ran it 30 times fresh (`mkdir` per run, no reuse): **30/30 times, the log
file was never created on disk at all** — not truncated, entirely absent.
Root cause: `fs.createWriteStream`'s internal `open()` is asynchronous;
since the whole call chain from stream creation to `process.exit(1)` never
yields to the event loop (no `await` anywhere in it, and `require()` is
synchronous), the pending `open()` callback never gets a turn to run before
the process is torn down, so even the buffered `run_start` write never
reaches a real fd. A simpler worst-case version (`flush-repro.mjs`, write
immediately after stream creation, no intervening work) reproduced the same
100%-loss result across 60 runs.

Impact, scoped precisely: the **exit code is unaffected** (still delivered
correctly — this doesn't touch B1's claim) and the `at` field is still
present *in the string* that was built (doesn't touch B9's "every emitted
line has `at`" claim, which is about lines that reach a sink) — but for
exactly these two fatal reasons, the run-log directory silently ends up
with **zero evidence** that the invocation happened at all, despite
`logSink` having been opened and `run_start` "logged." An operator scanning
`data/podcasts/unshaken/run-*.log` for a failed unattended run would find
nothing for a missing-secret failure, only the (correctly non-zero) exit
code and stderr from that one invocation, if captured.

Not filed as a new `bugs.md` entry by this pass (outside a
fix-verification agent's scope, per house convention observed in the
sibling `b4-b5.md` review) — flagging for triage. Does not change either
verdict above: B1's and B9's own stated fix contracts (unique filenames,
bare-invocation exit codes, no tee, `at` on emitted lines, stage roll-ups)
are all intact; this is a new, narrower gap in a third helper (`fatal()`)
that shares the same log sink.
