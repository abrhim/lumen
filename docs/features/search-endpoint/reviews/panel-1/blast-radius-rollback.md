## Evidence

All live probes 2026-07-21, SELECT-only, via worktree `.env` `DATABASE_URL` (`node -e` + `pg`, `ssl:{rejectUnauthorized:false}`).

**Trigger definitions exist in repo AND match live prod (BLA-1, BLA-5).**
`pg_get_functiondef()` for `lumen.update_verse_search_vector` and `lumen.update_entity_search_vector` returned bodies byte-equivalent (modulo header formatting) to `/Users/abram/code/lumen/.claude/worktrees/search-endpoint/scripts/setup-triggers-and-rls.sql:3-25`:

```
NEW.search_vector := to_tsvector('english', NEW.text);                                     -- verses
NEW.search_vector := to_tsvector('english', NEW.name || ' ' || coalesce(NEW.description,'')); -- entities
```

`pg_trigger` probe: exactly `trg_verses_search_vector` → `update_verse_search_vector` and `trg_entities_search_vector` → `update_entity_search_vector`; no other triggers on verses/entities/search_index/transcripts. So a restore source exists and is current — but the SQL file is mutable history, hence the pre-replacement `pg_get_functiondef()` capture into the migration log (BLA-1 fix). These are the only two `lumen.*` functions in prod; M2's function surface is exactly them plus new `normalize_kjv`. Both trigger functions fire on *entities* too — a broken M2 rollback blocks the unshaken branch's entity upserts (`scripts/ingest-podcast/load.mjs:33` deletes/reinserts the episode entity every weekly run), not just verse writes.

**M2 half-applied is coherent for Ring-2 (BLA-5).** `searchScriptures` (`packages/scripture/src/queries.ts:76-99`) is `WHERE v.search_vector @@ plainto_tsquery(...)` — evaluated per-row. With the new trigger live and backfill pending, untouched rows keep exactly their old vectors (old matches intact); touched rows carry superset vectors. No global consistency assumption exists, so the intermediate state loses nothing. This holds only if the trigger's dependencies (`kjv_variants`, `normalize_kjv`) are created first — the order BLA-5 pins.

**Ranking is NOT covered by H2 (BLA-4).** `searchScriptures` orders by `ts_rank(v.search_vector, plainto_tsquery(...))` with `LIMIT 10` (queries.ts:84-97). Concatenating `to_tsvector(text) || to_tsvector(normalize_kjv(text))` changes term frequencies and positions, shifting rank values; for queries with >10 matches (harness pins faith=810, spake=782) the returned 10 can change composition. H2 (`search-harness.test.ts:65-78`) pins count floors and one membership — nothing pins order. This is an observable Ring-2 behavior change the plan's "behavior... unchanged" claim doesn't cover.

**Shared-table ownership (BLA-3, BLA-6).** Live probe: `search_index` contains only `kind='episode'`, n=10, `collection_id='unshaken'` — every current row is owned by the other branch's pipeline. PK is `(kind, ref_id)` (`scripts/migrate-media-collections.mjs:35`). Ingest's own delete is correctly kind-scoped: `DELETE FROM lumen.search_index WHERE kind = 'episode' AND ref_id = $1` (`scripts/ingest-podcast/load.mjs:46`). Episode ref_id is the bare episode id (load.mjs:149-157) while plan decision 9 sets moment `ref_id = episode_id + '#' + seq_start` — so `ref_id LIKE episode_id || '%'` matches BOTH kinds; only kind-scoping is safe. The ingest is an idempotent weekly re-run ("weekly re-run", load.mjs:52-54) that deletes the episode entity (cascading transcripts, load.mjs:31-33) and reinserts captions — it knows nothing of `kind='moment'`, so re-ingest strands stale moments (BLA-6) and any M3/M4 mis-scoped delete strands the ingest's episodes (BLA-3).

**pg_trgm dependents after M1/M5 (BLA-2).** Extensions probe: installed today = pg_stat_statements, pgcrypto, plpgsql, supabase_vault, uuid-ossp — pg_trgm/unaccent absent, confirming plan Gap 2. After M1, catalog dependents of pg_trgm = the two new trgm GIN indexes (bare `DROP EXTENSION` fails; CASCADE eats the indexes). After M5, *runtime* dependents = searchAll tier-2 (`word_similarity`) and harness H5 — invisible to CASCADE, so extension rollback under a live M5 converts every name-bearing group query into a SQL error. Plan's graceful-degradation claim covers missing *kinds* only, not missing functions/relations. `unaccent` is build-time-only (M4 script inserts precomputed tsv into a plain table; `transcripts.search_vector` is the only GENERATED tsvector, migrate-media-collections.mjs:23, and it doesn't use unaccent) — so dropping unaccent breaks M4 re-runs, not reads.

**prepare:false claim verified (Hyperdrive × CREATE OR REPLACE FUNCTION).** `apps/web/app/lib/db.server.ts:31` sets `prepare: false` (with `fetch_types: false`), pinned by `apps/web/app/lib/__tests__/db.server.test.ts:29`; the live harness client also sets it (`search-harness.test.ts:42`). No app-side prepared statements → no "cached plan must not change result type" window during M2's `CREATE OR REPLACE FUNCTION`; plpgsql plan invalidation covers pooled backend connections. Residual in-flight-transaction exposure at <1k req/day is negligible. No action needed beyond keeping the existing pin.

**routes.ts contention is live, not hypothetical (BLA-7).** This worktree is on `feature/search-endpoint`; the main checkout is on `feature/unshaken-surfaces` with `apps/web/app/routes.ts` modified (uncommitted) plus untracked `spike.episode.tsx`/`spike.node.tsx` route modules. Current `routes.ts` is a 13-line array (`apps/web/app/routes.ts:3-13`); both branches append entries → guaranteed textual conflict at merge. Loss on this branch is test-caught — `apps/web/app/routes/__tests__/api-search.test.ts:157-163` greps routes.ts for `/api[/.]search/` — but only if the second-merging branch runs the first branch's tests; hence the both-suites-after-merge rule.
