## Evidence

All paths under `/Users/abram/code/lumen/.claude/worktrees/search-endpoint/`. Live probes run 2026-07-21 against prod via the read-only pooler DSN (SELECT only).

**API-1 — ts_headline markup (live).** `SELECT ts_headline('english', '…whosoever believeth in him <tag> & stuff', plainto_tsquery('english','believeth'), 'MaxFragments=1, MaxWords=18')` returned:
`"gave his only begotten Son, that whosoever <b>believeth</b> in him   & stuff"` — default `StartSel=<b>`; the literal `<tag>` in source text was silently swallowed and `&` passed through unescaped. A client cannot innerHTML this (delimiters indistinguishable from mangled document markup → XSS handoff on any source text containing markup) nor text-render it (users see literal `<b>`). Decision 8 (plan.md:57) specifies `MaxFragments/MaxWords` but not `StartSel/StopSel`, and neither harness asserts snippet format — the marker choice would ossify by accident. Neutral non-HTML markers make the snippet a plain-text contract the future UI and MCP can both consume.

**API-2 — ResolvedReference is not a wire shape.** `packages/scripture/src/resolve-reference.ts:13–20`: chapter level carries `verses: any[]` (Psalm 119 = 176 full verse rows inside a search response), verse level is `{ level: 'verse'; found?: boolean; [key: string]: any }` — optional discriminant plus open index signature. Plan decision 4/5 (plan.md:53–54) says the short-circuit goes "via existing `parseReference`/`resolveReference`" but never defines what `reference` serializes to. H11 (search-harness.test.ts:220–229) only checks `reference !== null`. The endpoint needs parse + existence, not resolution; navigation payloads are the destination route's job (same division the plan already applies to href construction).

**API-3 — cache headers.** House pattern for session-visibility responses: `apps/web/app/routes/scripture.tsx:367` and `book.tsx:34` set `Cache-Control: private, no-store` (SECURITY-3: rotated Set-Cookie must never be replayed to another visitor). `admin.users.tsx:51–54` shows rotation headers riding every outcome of `getSessionUser`. The search loader mirrors that path (plan.md:55) so its 200s can carry Set-Cookie while the body varies by entitlement (H8's leak class) — yet plan.md decision 5/7 and both harnesses say nothing about Cache-Control. This is the HTTP contract for the existing response, not the deferred KV-caching/abuse work in "Out".

**API-4 — `kind` collision.** Decision 5 (plan.md:54): `groups: [{ kind, results: [{ kind, … }] }]`. Group kinds come from decision 1 (plan.md:50): `scripture|people|places|topics|episodes|art|words`. Result kinds come from `search_index.kind` + entity/verse sources: `verse|jst?|person|place|…|episode|moment|artwork|strongs` — e.g. group `episodes` contains results of kind `episode` and `moment`; group `words` contains kind `strongs`; group `art` contains kind `artwork`. Same field name, disjoint enums, three inconsistent singular/plural pairings. `scope` (and the exported `GROUP_KEYS`) validates only the group enum; nothing in the plan names or exports the result-kind enum the UI must switch on for deep-linking.

**API-5 — payload divergence (live).** Existing prod row: `search_index` kind=`episode` has `payload = {"episode": "unshaken-25hrVBU3Vz8"}` — key `episode`, while plan.md:58 specifies moment payload key `episode_id`. Artwork metadata (entity `art:met-471845` — note the `art:` prefix is the entity id itself, so `ref_id` = entity id is consistent) offers both `image_url` and `thumbnail_800_url`; plan.md:54 says only "thumbnail URL". JST deep-link making exists in prod (`jst-gen-1-1` metadata: `{"verse_id": "gen-1-1", "change_type": "substitution", …}`) but decision 1's `variant:'jst'` flag has no stated location (result field vs payload) and the canon-verse counterpart is undefined. What each kind's payload MUST contain for deep-linking: verse → `verse_id` (+ `variant`, and for JST the target canon `verse_id`); moment → `episode_id`, `t_start_s`, `t_end_s` (numbers); episode → `episode_id`; artwork → `refs` (book/chapter for `/scripture/:book/:chapter/art`) + one named thumbnail field; strongs → `strongs_no` (routes to existing `word/:no`). None of this is currently written down as a typed contract.

**API-6 — string typing (live).** Through the pooler with postgres.js defaults: `search_index.payload` came back as the string `"{\"episode\":\"unshaken-25hrVBU3Vz8\"}"`, and `transcripts.t_start_s` as string `"8990.650"`. The plan itself flags the trap (plan.md:19) and H13 (search-harness.test.ts:242–252) pins `typeof t_start_s === 'number'` — but only for moments; an unparsed artwork/strongs/episode payload would ship as a JSON-encoded string field and no assertion would fire.

**API-7 — validation asymmetry.** plan.md:54: "`scope` optional CSV of group keys (unknown keys 400), `limit` per-group 1–25 default 8 (clamped, never 500)" — strict-reject and silent-clamp side by side on one endpoint. H14 tests (api-search.test.ts:76–83) cover `limit=999|0` and `scope=nonsense` but not `limit=abc`, `scope=` (empty string), `scope=scripture,,people`, or `scope=scripture, people` (space). Whatever the choice, it must be specified, symmetric where possible, and pinned — otherwise the implementation's accident becomes the contract.

**API-8 — empty-groups ambiguity.** plan.md:54 "Zero hits = 200 with empty groups" vs plan.md:42 "empty group, never 500". H11 (search-harness.test.ts:224) asserts `verse.groups.every(g => g.results.length === 0)` — groups array populated with empty `results`. The endpoint test (api-search.test.ts:85–90) asserts `body.groups` equals `[]` — but only because the mock returns `EMPTY_RESPONSE = { groups: [] }`, so the real shape is unpinned. Stable-shape grouping (always exactly the scoped keys, fixed order) is the version-safe choice: the future UI renders section scaffolding deterministically and additions of new group keys are detectable as additive.

**API-9 — error codes.** plan.md:54 defines errors as `{error}` only; api-search.test.ts:66–74 asserts merely `body.error` truthy. plan.md:119 records the house lesson "Workflow results keyed by index/enum, never prose echo." An MCP client distinguishing "query too short" from "unknown scope" today has only English prose to match on; message wording then becomes unchangeable.

**API-10 — moment id stability.** plan.md:58: `ref_id = episode_id + '#' + seq_start`, windows produced by parameterized heuristics (500-char target, 2.0s gap, 200–800 bounds — Q2 explicitly still open) with idempotent per-episode rebuild. Any parameter tuning re-partitions and renumbers windows, silently retiring every previously issued moment `id` while all other kinds' ids (verse `john-3-16`, entity `art:met-471845`, `G26`, `unshaken-4pSrikfJ5Yw`) are durable. The contract should say which ids a client may persist/bookmark; the plan's own payload (`episode_id` + `t_start_s`) is the durable deep-link and should be documented as such.
