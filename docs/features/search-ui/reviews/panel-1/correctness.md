## Findings

| ID | Severity | Where | Problem | Fix |
|----|----------|-------|---------|-----|
| CU-1 | high | plan.md:26 (`v1\|qhash\|tier\|score\|id`); search.ts:271 (`ORDER BY u.tier, u.sub, u.score DESC, u.id`), :369-370 (episodesLeg same); api-search-cursor.test.ts:59 (`encodeSearchCursor({q,scope,tier,score,id})` — no `sub`) | The pinned cursor format omits `sub` (jst/moment demotion), but the *actual* per-leg total order for the `scripture` and `episodes` groups is `(tier, sub, score DESC, id)`. Live-verified: for `q=faith, scope=episodes`, row 0 is the one episode hit (tier=3,sub=0,score=0.1636) and every subsequent row is a moment (tier=3,sub=1,score≈0.013-0.016) — scores are not ordered by `sub`, so a `(tier,score,id)`-only keyset predicate can silently skip or duplicate rows exactly at a sub-boundary page split. Not exercised by the given F1/F5 fixture (`q=faith,scope=scripture` has 810 verse hits before any jst row — the boundary is never reached at `limitPerGroup=25`). | Add `sub` to the cursor payload and the WHERE predicate for `scripture`/`episodes` (or thread the exact per-leg ORDER-BY tuple through); add a live pin using a query whose verse-hit count crosses a page boundary near the jst/moment transition. |
| CU-2 | high | search-cursor-harness.test.ts:12-17 (`loadDsn`, regex `/^DATABASE_URL="?([^"\n]+)"?/m`) vs apps/web/.env (only defines `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`) | The one harness able to catch CU-1 against live data is itself broken: it looks for a `DATABASE_URL` key that does not exist in `apps/web/.env` (the sibling `search-harness.test.ts` correctly uses `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`; a repo-root `.env` does have `DATABASE_URL` but that's the admin DSN, not what this file reads). Live-verified by running the suite: `Error: no DATABASE_URL in apps/web/.env` at `loadDsn`, all 3 tests skipped/failed in `beforeAll`. This is exactly the "harness-origin bugs are the top provenance class" pattern the plan itself calls out. | Fix the regex/var name to match `search-harness.test.ts`'s pattern before implementation starts; re-run to confirm the suite fails RED for the right reason (missing `after`/`nextCursor`), not a config typo. |
| CU-3 | high | plan.md:25 (scope-line click = toggle-exclude), :70 (Q5); api.search.tsx:53-56 (`scope_unknown` on any empty CSV segment); build-mockup.py:268-270 (scope `<a>` = plain in-page anchor, no exclude listener anywhere in the script) | Excluding all 7 groups has no valid representation in the shipped contract. Live-verified: `GET /api/search?q=faith&scope=` → `400 {"code":"scope_unknown"}`. The click-to-exclude gesture computes the URL's `scope=` as GROUP_KEYS minus excluded, so excluding everything produces exactly this empty string. Neither the plan's Q5 nor the "human-approved" mockup (which never implements the exclude gesture at all — its `.scope` items are inert anchor-jump links) defines a floor. A naive implementation either 400s the user's own page or silently reverts to searching *everything* (the opposite of "exclude everything") when it drops the empty param. | Enforce a floor of ≥1 included group client-side (disable/no-op excluding the last remaining group), and pin the boundary in F7's harness. |
| CU-4 | high | plan.md:10 (A6 prior-learning: moment ids are response-scoped); search-endpoint/plan.md:104 (A9: "Prod still holds 178 pre-fix >800 windows — remediation = the deferred COMMIT=1 M3 re-run (with the A6 id-churn consequence)"); search-ui plan.md F10 (only covers deep-link href, not cursor validity) | A moment re-window is a documented, still-pending, imminent operational event for this exact corpus (search-endpoint plan A9), and A6 already establishes moment ids re-key on every re-run. The episodes-group cursor is keyed on `(tier,score,id)` where `id` *is* the moment id. If a re-window runs between a user's page-1 fetch and a page-2 "More" click, the cursor decodes fine (q/scope hash still matches) but no longer corresponds to a real position — post-rewindow scores for overlapping content change too — so page 2 can silently duplicate or skip moments with zero user-visible error. No F-number or harness assertion covers this. | Add a data-generation stamp to the cursor (e.g. a moments-build version) so a stale cursor after a re-window fails closed with a clear "results may have changed, restart" state instead of silently mis-paginating; at minimum dedupe client-side on `(episode_id, t_start_s)` across appended pages. |
| CU-5 | med | search-cursor-harness.test.ts:67-74 (`cursor codec round-trips` — `toMatchObject({tier:3, id:'alma-32-21'})` never asserts `score`) | The one pinned round-trip test for the cursor codec doesn't check that `score` survives encode→decode. Live-verified score ties are common and dense (e.g. 6-10-way ties at identical `ts_rank` values within 25-row windows for `q=faith`), so the assigned lens item — "is `(tier,score,id)` a stable total order through postgres.js float serialization" — has zero coverage. Any precision loss in the float8 round-trip (formatting, truncation) would manifest as duplicate/gapped rows exactly at a tie boundary, and this test would still pass. | Extend the round-trip assertion to include `score` with a value chosen to stress float precision (e.g. a score pulled from a live tied pair), not a hand-picked `0.123456`. |
| CU-6 | med | api.search.tsx:42-49 (`Q_MIN=2` → 400 `q_length`); search.ts:520 (`searchAll` only slices to 200, no floor); plan.md Q4 (loader calls `searchAll` directly, bypassing api.search.tsx) | Because `/search`'s loader calls `searchAll` directly rather than going through `api.search.tsx`, the two entry points diverge on the *same* input: `q=a` (1 char) is a 400 on `/api/search` but a live, fully-executed federated search on `/search`. `search.loader.test.ts` only pins the empty-`q` case (lines 69-73); nothing pins the 1-char or 201+-char boundary for the page route. | Extract `Q_MIN`/`Q_MAX` (or the whole validation block) into a shared helper both `api.search.tsx` and `search.tsx`'s loader call, so the two surfaces can't silently disagree. |
| CU-7 | med | api.search.tsx:67 (`limitPerGroup = 8` default when `limit` param absent); plan.md:25 (adaptive limit 5-7→8,3-4→12,2→18,1→25), :26 (infinite scroll via `/api/search` `after`) | Single-scope cursor pagination (`after`) is served by `/api/search`, a *separate* request from the SSR page load. Nothing in Scope or the failure-mode list says the client must carry `&limit=` on every "More"/sentinel fetch to match the density the page opened with (25 for an isolated single group). If the pagination fetcher omits it, page 1 shows 25 items and every subsequent page silently shrinks to the API's default of 8 — an inconsistent, jarring page-size change mid-scroll that no F-number would catch. | Pin the pagination fetch to always include `limit=` derived from the same `adaptiveLimit(scope.length)` the page used, and add a harness assertion that the "More" URL includes it. |
| CU-8 | med | plan.md:23-24 ("skeleton only after 300 ms"; modal "Enter → navigate", "on `/search` itself hotkeys focus the inline input") | The plan never states whether editing the query on `/search` itself does a debounced live update (a fetcher, implied by the "skeleton only after 300ms" idiom) or requires explicit submission. If it's a live-updating fetcher, nothing addresses the out-of-order case where a debounced in-page update is still in flight when the user hits Enter (or clicks a scope-exclude link) and triggers a second, competing request/navigation — stale results could land after fresher ones. | Add an explicit decision + F-number: name the update mechanism, and specify that any in-flight live-update request is aborted/ignored once a navigation-triggering action (Enter, scope click) fires. |

## Evidence

- **CU-1 / episodes sub-boundary (live probe, read-only GET/SELECT via `lumen_read`):** ran the exact `episodesLeg` ORDER BY against `lumen.search_index` for `q='faith'`:
  ```
  0: episode sub=0 score=0.1636026501655580 id=unshaken-jMYk190JBys
  1: moment  sub=1 score=0.0155480559915304 id=unshaken-8SvK7L87o1A#1945
  2: moment  sub=1 score=0.0149804847314954 id=unshaken-25hrVBU3Vz8#3551
  ...
  ```
  `count`: 1 episode hit, 220 moment hits for `faith`. A `(tier,score,id)`-only predicate reconstructed from a cursor minted at the sub=0 row (score 0.1636) would require every subsequent row to have `score < 0.1636` to appear "after" it — true here by luck (moment scores are all far lower), but nothing in the schema/query guarantees `sub=0` scores dominate `sub=1` scores in general; the ordering correctness depends entirely on `sub` being part of the comparison, not on this incidental score gap.
- **CU-1 / scripture-leg fixture blind spot (live probe):** `verse_hits=810, jst_hits=348` for `q='faith'`. With `limitPerGroup=25` (the F1 test's own parameters), page 1 and page 2 are both pure-verse (`sub=0`) — the fixture cannot reach row 810 where `sub` flips to 1, so the pinned F1 test structurally cannot catch a missing-`sub` bug even once the harness itself is fixed (see CU-2).
