# PANEL-1 / SPECIALIST — security review of docs/features/search-ui/plan.md

Lens: authn/authz/input validation. Plan is pre-implementation (harness red-first);
findings target the PLAN's spec/harness completeness, not code that doesn't exist yet.

| ID | Severity | Where | Problem | Fix |
|----|----------|-------|---------|-----|
| SU-1 | high | plan.md F1–F5 (lines 47–51); search.ts `entityLeg` collection gate (line 319) + order/limit (lines 328–329); search-endpoint plan.md decision 6 (line 50) | No failure mode/harness assertion pins that the new keyset (`after`) predicate is ANDed **inside the same per-leg WHERE** as `collection_id = ANY(visibleCollections)`, re-derived fresh from the *current* session on every request. A cursor carries only `q`/`scope`/`tier`/`score`/`id` (plan.md line 26) — never visibility — so the architecture is sound only if the implementer inserts the predicate alongside the existing gate rather than as an outer wrapper around an already-limited/gated subquery (which would also silently break pagination correctness at a visibility boundary). No test exercises "cursor minted under a wider visibility (admin, or a collection later flipped to `public=false`) replayed by a narrower session." |
| SU-2 | med | api-search-cursor.test.ts F3/F4 (lines 71–98); no equivalent test for a well-formed, correctly-bound cursor pointing at a real-but-invisible row | Cursor validation must be pure comparison math (base64/format decode + qhash(q,scope) match) — it must never look up "does this id exist / is it visible" to produce a friendlier error, or that lookup becomes an oracle: an attacker who can distinguish "cursor_mismatch" (structurally fine, wrong q/scope) from a hypothetical "cursor references nothing visible" response could enumerate whether admin-only/embargoed content matching a query exists. The plan never states decode must stay stateless/DB-free, and no harness case forces this. |
| SU-3 | med | plan.md line 26 (`v1|qhash|tier|score|id`); search.ts `escapeLike`/`anyOf` (lines 136–144) establish the file's parameterization discipline; nothing analogous stated for cursor fields | Decoded `id` (attacker-controlled bytes, since it round-trips through a client-suppliable base64url blob) has no declared charset/length constraint before reaching the keyset SQL predicate, and the pipe-delimited format has a delimiter-collision risk if `id` ever contains literal `\|`. Also no length cap on the `after` query param itself (unlike `q`'s 2–200 and `limit`'s [1,25] clamp — api.search.tsx lines 47–49, 74). |
| SU-4 | high | search.loader.test.ts F6 (lines 55–58) only asserts `Cache-Control: private, no-store` on the `?q=faith` happy path; no assertion on the thrown-400 (`scope=bogus`, line 91), empty-q empty-state (line 69), or reference-short-circuit (F13, line 112) response paths; search-endpoint plan.md decision 5 states the invariant applies to "every response (200/400/500)" (line 49, "house SECURITY-3 pattern") | `/search` renders session-varying visibility (admin sees extra collections). If any loader exit path is missing the header, a shared/edge cache (this ships on Cloudflare) can serve one session's result set to a different session for the identical URL — a cross-user data leak, not just staleness. The harness only proves the header on one of five distinct exit branches. |
| SU-5 | med | build-mockup.py `esc()` (line 210, escapes only `& < >`, not quotes) + `marks()` (line 211) build `<mark>` via `innerHTML` string-splicing; search.loader.test.ts F12 (lines 96–109) expects `parseMarks` to return typed `{mark, text}` segments instead | The approved mockup is explicitly cited as binding for visual decisions (task brief item 5), and its snippet renderer is a raw-HTML-string/`innerHTML` technique that would be an XSS vector if ported literally into React (`dangerouslySetInnerHTML` with an incomplete escaper). The `parseMarks`-returns-segments shape is the safe contract, but nothing in the plan explicitly forbids reassembling those segments into an HTML string instead of real React children, and no test asserts the renderer never uses `dangerouslySetInnerHTML`/`innerHTML` for snippet or title text. |
| SU-6 | low | plan.md F9 (line 55) only specifies the "don't hijack" guard for `/`; login.tsx lines 131–143 is the app's only non-`/search` text input (passwordless email OTP/magic-link — confirmed no `type="password"` field exists anywhere in `apps/web/app`) | `⌘K` isn't explicitly covered by the stated per-input guard, even though a modifier chord is unlikely to be typed literally. Low impact given the app is passwordless, but the same "focused input/textarea suppresses global hotkeys" guard should explicitly cover `⌘K` too, not just `/`, so mid-entry on `/login`'s email field isn't interrupted. |

## Evidence

**Live probe (read-only, `lumen_read`, SELECT only)** — confirms `current_user = lumen_read` and that all 8 collections are currently public, so SU-1's cross-visibility scenario is not exploitable *today* but is architecturally live via `ADMIN_COLLECTIONS` entitlement (`apps/web/app/lib/collection-access.server.ts`) and the `public=false` kill switch (search-endpoint plan.md decision 6, line 50):

```
user: lumen_read
[
  {"id":"art","public":true},{"id":"canon","public":true},{"id":"jst","public":true},
  {"id":"naves","public":true},{"id":"openbible","public":true},{"id":"phase-b","public":true},
  {"id":"strongs","public":true},{"id":"unshaken","public":true}
]
```
(DSN read from `apps/web/.env` var `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`, `ssl:{rejectUnauthorized:false}`.)

**SU-1** — `packages/scripture/src/search.ts` `entityLeg` (lines 276–331) shows the established pattern: `collection_id = ANY(${anyOf(visible)})` (line 319) lives in the SAME inner-subquery WHERE that also drives `ORDER BY tier, sub, score DESC, id LIMIT ${limit}` (lines 328–329). This is exactly where a keyset predicate (`(tier, sub, score, id) > (…)`) must be inserted for the gate and the pagination cursor to compose correctly and safely. `searchAll`'s combined-statement/per-group-fallback architecture (lines 518–614) means a bad predicate value degrades that one group to `{results: [], error}` rather than a 500 (COR-1/H17), which is reassuring, but doesn't substitute for a test that a cursor cannot be used to widen the *set* of collections a leg's WHERE will match. `visibleCollections` is computed fresh per request in `api.search.tsx` (lines 92–100) from the current session, never persisted — the cursor payload (plan.md line 26) correctly excludes it — but nothing enforces an implementer keeps it that way once cursor code is added.

**SU-2** — `api-search-cursor.test.ts` F3 (lines 71–81) and F4 (lines 83–98) test (a) structurally-garbage cursors → `cursor_invalid`, and (b) cursors correctly formatted but bound to a different `q`/`scope` → `cursor_mismatch`. Neither tests a cursor that is well-formed AND correctly bound to the request's `q`/`scope` but whose `tier/score/id` triple doesn't correspond to any row the *current* session can see. The safe behavior (silently continue/empty page, same as any other position past the visible set) is implied by "keyset predicate is pure comparison, no row lookup" but is never stated as a MUST or pinned by a test.

**SU-3** — `search.ts` lines 135–144 (`escapeLike`, `anyOf`) are the file's existing documented discipline for turning attacker/DB-adjacent strings into safe SQL fragments (SEC-5 in the endpoint plan). The search-ui plan's cursor format (`v1|qhash|tier|score|id`, plan.md line 26) has no equivalent stated discipline for the decoded `id` field, which — unlike existing ids that are always DB-sourced — arrives directly from client input via `after`. `api.search.tsx` bounds `q` (lines 46–49) and `limit` (lines 67–75) explicitly; no analogous bound is proposed for `after`.

**SU-4** — `search.loader.test.ts`: the only `Cache-Control` assertion is lines 55–58 (`?q=faith` case). The empty-state branch (line 69, "empty q renders the empty state without calling searchAll") and the thrown-400 branch (line 91, "unknown scope key in URL → thrown 400 response") return through different code paths (`data.headers` vs. a thrown `Response`), and neither is checked for the header. `search-endpoint/plan.md` line 49 states the header is required on every 200/400/500 for the sibling API route — the UI plan (line 21) commits to the same header for `/search` but the harness doesn't hold every branch to it.

**SU-5** — `build-mockup.py` lines 210–211 and 254–271 confirm the mockup's snippet/zero-state rendering is done by hand-building HTML strings and assigning `.innerHTML`, with an `esc()` that only covers `& < >`. This file is cited by the task brief as binding for *visual* decisions; the risk is scope creep of its *implementation technique* into the React port. `search.loader.test.ts` F12 (lines 96–109) is consistent with the safe alternative (typed segments for element-based rendering) but doesn't positively assert the renderer avoids `dangerouslySetInnerHTML`.

**SU-6** — `apps/web/app/routes/login.tsx` lines 131–143 is a native `<input type="email">` (passwordless OTP/magic-link flow, matching `auth-email-decision` memory); `grep -rn 'type="password"'` across `apps/web/app` returned no matches, confirming no password field exists in this codebase. Risk is narrow but plan.md F9 (line 55) states the guard only in terms of `/`.
