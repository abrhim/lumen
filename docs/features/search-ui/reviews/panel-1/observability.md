# Panel-1 / Observability review — search-ui plan

Reviewed: `docs/features/search-ui/plan.md` against the shipped `/api/search`
(`apps/web/app/routes/api.search.tsx`), `packages/scripture/src/search.ts`,
the red-first harness, and the approved mockup source
(`build-mockup.py`). Lens: client + server observability.

| ID | Severity | Where | Problem | Fix |
|----|----------|-------|---------|-----|
| OU-1 | high | `api.search.tsx:109-139` (unconditional `logEvent("search_executed",...)`); plan.md Files-touched for `api.search.tsx` (add `after` passthrough) | `search_executed` carries no `after`/page-depth/source field. Once cursor pagination ships, every "More"/infinite-scroll continuation re-enters this same loader and logs an indistinguishable `search_executed` row. Because F2 forces exactly one scope group whenever `after` is set, `result.groups` collapses to length 1 (`searchAll`, `search.ts:525`), so an exhausted last page (0 new rows) computes `zeroResult: true` even though the original query had many hits — corrupting the exact metric OBS-1 names as "the one structured line the relevance-tuning loop feeds on" (search-endpoint plan.md:54). Query-volume/hit-count aggregates are also inflated once per scroll. | Add `after: boolean` (or `page`/`depth`) and a `source` field to the logged payload; exclude `after`-bearing rows from zero-result denominators, or split them into a separate `search_paginated` event. |
| OU-2 | high | plan.md Scope §"`/search` route... URL-driven `?q&scope`" (line 21) — no input-model spec; `build-mockup.py:284` (`input.addEventListener("input", ()=>{clearTimeout(tmr); tmr=setTimeout(()=>render(input.value),160)})`) | The approved mockup wires the on-page query box to live-filter on every settled keystroke (160ms debounce). The plan never states whether the real `/search` page's inline input is Enter/submit-only (like the modal) or mirrors this per-keystroke behavior. If it mirrors the mockup, each settled keystroke re-runs the loader (or a client fetch) and logs its own `search_executed` — not a double-log but an N-way log storm of partial-prefix queries ("f","fa","fai","faith") polluting the OBS-1 feed far worse than a simple duplicate. No F-number in the harness (F6-F14) pins single-log-per-logical-search across a typing session. | Pin the input model explicitly in the plan: either submit-only editing on `/search` (matches modal, avoids the risk entirely) or debounce + log-on-settle-only with an explicit trigger reason; add a harness assertion that `search_executed` does not fire once per keystroke. |
| OU-3 | med | app-wide: no `Sentry`/`analytics`/client `logEvent` anywhere in `apps/web/app`; `root.tsx:85-119` `ErrorBoundary` renders fallback UI only, never reports | No client-side error telemetry exists anywhere in the app (pre-existing, confirmed by grep — only server `console.error`-based `logEvent`, `log.server.ts:1-7`). This feature is the first to add a client-initiated fetch that can fail *after* first paint (pagination "More"/infinite-scroll: network error, 500, `cursor_invalid`/`cursor_mismatch`) plus a stateful modal (hotkeys/focus trap). Not covered by the plan's "Out" list (which names "search analytics UI," a different thing). Currently a failed load-more is invisible to the team. | Either have the plan explicitly accept this gap in writing (a reviewed decision, not silence), or add a minimal client-side failure signal for the pagination-fetch path specifically (e.g. a beacon/logEvent-equivalent on fetch rejection or non-2xx). |
| OU-4 | high | plan.md Prior-learnings (line 17, "the scope-exclude gesture is the only 'cull' affordance we ship now"); `api.search.tsx:125` `scope: scope ?? null` | `search_executed`'s `scope` field records only the resulting scope at request time — it cannot distinguish a deliberate exclude-click, an "isolate to X" pill click, a shared link landing with `?scope=` preset, or back/forward navigation. The plan frames scope-exclude as the deliberate, sole instrumented signal for validating researcher-loop demand ahead of the future notes feature (competitor learnings, line 17). Shipping it without a way to measure *which* interaction produced a given scope value defeats the stated purpose of the bet. | Add a `scopeTrigger`/`facetAction` field (`exclude`\|`isolate`\|`link`\|`nav`) logged only from the client-driven navigation that originates the change, distinguishing active gestures from passive scope state. |
| OU-5 | med | `api.search.tsx:34-36` (`badRequest`, no `logEvent`); the three new codes this plan adds — `cursor_scope`, `cursor_invalid`, `cursor_mismatch` — per Files-touched (line 33); search-endpoint plan.md:72 "SEC-9 deferred-out-of-scope (abuse hardening deferred)" | Every validation 400 (including the pre-existing `q_required`/`q_length`/`scope_unknown`, lines 44/48/56) already goes unlogged — this plan's three new cursor codes inherit that silence with no discussion. Two risks named elsewhere in this plan's own carried-forward learnings then have zero prod signal: a future cursor version-byte bump (line 14, "version-bumped keys need same-commit test pins") would silently 400 every outstanding pagination cursor with no way to see the spike's cause in logs; and with rate-limiting/abuse hardening explicitly deferred on this public endpoint (SEC-9), malformed/tampered-cursor probing is equally invisible. | Add `logEvent("search_cursor_rejected", {code, qLen, scope})` at the three new 400 sites — never the raw cursor value, matching F3's "never echoed raw" invariant. |
| OU-6 | high | plan.md Files-touched (`search.tsx` new, `api.search.tsx` edit — two independent `searchAll` call sites); search-endpoint plan.md:54 "the loader logs it" (decision 10); `api.search.tsx:109-139` (full OBS-1/2/3 block: `search_executed` + `search_group_degraded` + `search_failed`) | Q4 has `/search`'s page loader call `searchAll` directly rather than self-HTTP to `/api/search` — correct for avoiding a literal double-log of `search_executed` (F6), but it also means the ~30-line OBS-1/2/3 logging block (per-group degraded logging, `zeroResult`/`combinedError` computation, the `search_failed` catch-path contract) now needs an independent, faithful copy in `search.tsx`. The plan's F6 only asserts `search_executed` fires once; nothing pins that `search_group_degraded` (OBS-2: "a degraded group must never be mistaken for zero hits") and `search_failed` also fire identically from the page loader, which is the majority-traffic path (SSR first paint) versus `/api/search` (pagination only). An easy-to-miss omission on copy/reimplementation silently halves degraded-group visibility for most real user searches. | Extract the OBS-1/2/3 logging block into a shared helper (e.g. `logSearchExecuted(result, {q, scope, visibility, userId, source})`) called from both loaders; add an explicit harness assertion that `search_group_degraded`/`search_failed` fire identically from both call sites. |

## Evidence

- `apps/web/app/routes/api.search.tsx:34-36` — `badRequest()` returns JSON, never calls `logEvent`.
- `apps/web/app/routes/api.search.tsx:44,48,56` — `q_required`/`q_length`/`scope_unknown` all return via `badRequest` with no logging (existing pattern the plan's 3 new cursor codes would inherit silently).
- `apps/web/app/routes/api.search.tsx:109-139` — the full OBS-1/2/3 block: per-group `search_group_degraded` (line 120), `search_executed` (lines 123-139) including `zeroResult` computed from `result.groups.every((g) => g.results.length === 0)` (line 130) and `scope: scope ?? null` (line 125, no trigger/source discriminator).
- `apps/web/app/routes/api.search.tsx:149-156` — `search_failed` logged in the `catch`, page-loader parity for this is not asserted anywhere in the harness.
- `apps/web/app/lib/log.server.ts:1-7` — `logEvent` is `console.error`-based, server-only; no client analog exists anywhere in the codebase (verified via grep across `apps/web/app` for Sentry/analytics/window.onerror/reportError — only route-level `ErrorBoundary` components, which render fallback UI and do not log, confirmed at `apps/web/app/root.tsx:85-119`).
- `packages/scripture/src/search.ts:525` — `const groups: SearchGroup[] = scope.map(...)`, confirms `result.groups` has exactly one entry whenever `scope` has one key (the F2-mandated shape for any `after`-bearing request), which is what makes OU-1's `zeroResult` miscount concrete rather than speculative.
- `apps/web/app/routes/__tests__/search.loader.test.ts:59-63` — F6's "exactly once" assertion mocks `searchAll`/`logEvent` and only checks the loader's own call count in isolation; it cannot and does not assert cross-file non-duplication with `api.search.tsx`, nor does any test assert `search_group_degraded`/`search_failed` parity between the two loaders (OU-6) or log-volume behavior for a typing session (OU-2).
- `apps/web/app/routes/__tests__/api-search-cursor.test.ts:71-81` (F3) — asserts malformed cursors return `400 cursor_invalid` and never echo the raw value, but does not assert (and the plan does not scope) any `logEvent` call on that path (OU-5).
- `/private/tmp/claude-501/-Users-abram-code-lumen/e08e0036-b9be-449d-a5f0-35fab2f84789/scratchpad/build-mockup.py:284` — `input.addEventListener("input", ()=>{clearTimeout(tmr); tmr=setTimeout(()=>render(input.value),160)})`, the approved mockup's live-as-you-type interaction pattern that plan.md never confirms or rules out for the real `/search` page's inline input (OU-2). `render()` itself (mockup line 250) is local/mock-data only — no `fetch`/`/api/search` call exists in the mockup — so this is evidence of the *approved interaction pattern*, not proof the real implementation performs a network round-trip per keystroke; the plan's silence on which it will be is the finding.
- `docs/features/search-endpoint/plan.md:54` — decision 10, OBS-1 wording: `search_executed` is "the loader logs it," the log line OBS-1 exists specifically to feed the relevance-tuning loop (motivates OU-1/OU-2's severity).
- `docs/features/search-endpoint/plan.md:72` — "SEC-9 deferred-out-of-scope (abuse hardening deferred; noted for the UI feature)" (motivates OU-5).
- `docs/features/search-ui/plan.md:14` — "Version-bumped keys need same-commit test pins — cursor format version byte gets a pinned decode test" (motivates OU-5's version-bump-staleness scenario).
- `docs/features/search-ui/plan.md:17` — "The scope-exclude gesture is the only 'cull' affordance we ship now" (motivates OU-4).
- `docs/features/search-ui/plan.md:28` — the "Out (deliberate)" list contains "search analytics UI" but not client-error telemetry or a `search_executed` provenance/trigger field — confirms OU-3/OU-4 are not pre-excluded.
