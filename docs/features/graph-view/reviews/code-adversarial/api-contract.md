## Stance

**CAPI-1 (material).** Verified `apps/web/app/routes/scripture.tsx:196`: a charset-invalid `?graph` value sets `graphId = null`, which at line 223 also nulls the `graph` promise and at line 515 skips mounting `<GraphOverlay>` entirely — indistinguishable from no `?graph` param at all. The plan's public-contract line ("Invalid/unknown entityId → overlay 'not found' state … no 404 page") textually bundles "invalid" with "unknown" under one promised UI outcome, and Failure Mode 3 only enumerates "unknown," leaving room to argue charset-garbage was meant to fall under the `?verse`-style "malformed = treat as absent" precedent (API-3's accepted asymmetry). That reading is defensible in isolation, but it doesn't survive contact with CAPI-5: because the client's optimistic `pendingGraph` parse skips the same regex, a malformed id currently opens the overlay skeleton and then silently vanishes once the loader resolves — worse than either "always not-found" or "always absent." Fix cost is a few lines (keep a synthetic not-found id, or gate mount on param presence rather than regex validity); benefit is closing a real, observable UX bug plus resolving the contract ambiguity in the direction the text more naturally supports. Fix it.

**CAPI-2 (noise, downgraded from the panel's Medium).** Confirmed in `scripts/backfill-neo4j-collections.mjs:254-259`: edges report `{pgRows, matched, conflictingKeys}`, no `missing` key, while nodes carry `missing` per-type. But `backfill_done` is a log line read by a human running `--dry-run` (plan Q3), the script is explicitly scoped as sole-developer tooling with minimal observability by design (OBS-9 resolution), and no test or downstream code parses these keys by name (`scripts/__tests__/backfill-collections.test.mjs` asserts none of them). `missing` is one subtraction away for the reader. Renaming/adding a field is cheap, but the benefit is purely cosmetic doc-accuracy for a manually-read report — not worth a review cycle. If touched at all, fold into an unrelated backfill edit rather than a standalone fix.

**CAPI-3 (out-of-scope).** The independent `GraphPanelData` re-declaration in `scripture.tsx:71-73` and `GraphOverlay.tsx:11-13` is real, but this is API-2 from the plan's own Decisions table, already adjudicated: "rejected-with-rationale — doc-only fix; no consumer conflates the three shapes." The code-panel finding re-raises a concern the plan's human gate already declined to fix. One honest gap: the rejection's own rationale says the divergence is "noted as intentional in code comment," and no such comment exists near either declaration — that's a minor unfulfilled term of the rejection, worth a one-line comment if anyone is in the file, but not a new finding to act on independently.

**CAPI-4 (noise).** Confirmed `packages/scripture/src/graph/index.ts:3-12` exports `NeighborhoodNode`, `NeighborhoodEdge`, `GRAPH_ENTITY_TYPES`, `GRAPH_NODE_TYPES`, `GRAPH_REL_TYPES` beyond the plan's documented `getNeighborhood`/`NeighborhoodResult`/`NeighborhoodOpts` trio. Surplus exports carry no runtime risk and are plausibly needed by future collection-scoped callers building valid `nodeTypes`/`relTypes` options without re-declaring the allowlists. Purely a documentation-completeness gap; not worth a code change, at most a plan-doc line update.

**CAPI-5 (material).** Confirmed `scripture.tsx:318-323`: `pendingGraph`'s optimistic parse reads `p.get("graph")` raw, with no `GRAPH_ID_RE` test, unlike `?verse`'s `parseVerseParam`/`validVerse` pair which the file's own comment says intentionally "shares the loader's grammar AND its membership rule, so the optimistic state never disagrees with what the server will decide." That discipline wasn't extended to `?graph`. Concretely reachable any time a user free-types or corrupts a `?graph` value: skeleton opens optimistically, then disappears with zero explanation when the loader resolves `graphId: null`. Fix is exactly mirroring the existing `?verse` pattern — same file, same idiom, near-zero risk. Fix it, and note it interacts with CAPI-1: whichever not-found/absent semantics CAPI-1 lands on, CAPI-5's fix should route through the same decision so optimistic and server states keep agreeing.

**CAPI-6 (material).** Confirmed `get-neighborhood.ts:134`: `centerUnion = labelUnion(GRAPH_ENTITY_TYPES)` uses the full 13-label set (including `StrongsWord`/`JstReading`), while `nodeUnion` (neighbors) correctly uses the restricted `GRAPH_NODE_TYPES`, which excludes them. The plan's Goal line even flags words as a forward-looking extension ("later words"), and Scope explicitly puts "Word/Strong's node surfaces" Out for this feature. It's true a surface is not the same as center-ability, and true that no current entry point (verse panel, chips, chapter button) ever passes a word id — but `?graph=<id>` is a public URL parameter accepting any string matching `GRAPH_ID_RE`, independent of what UI generates it, so this isn't hypothetical, just not yet exercised by first-party links. Because `GRAPH_REL_TYPES` has no word-specific relationship types wired in, centering on a word today would return `found:true` with a mostly-empty graph — a half-supported experience squarely in the area the plan reserved for a future, differently-designed feature. The asymmetry with `nodeUnion` also reads as reuse-of-convenience (grabbing the readily-available full label list) rather than a deliberate choice, which is exactly the kind of scope leak that's cheap to close now and gets more entangled to unwind once a real word-surfaces feature exists. Fix: a `CENTER_TYPES` (or reuse `GRAPH_NODE_TYPES`, extended with `ChapterSummary`/etc. as needed for the chapter-summary entry point) excluding `StrongsWord`/`JstReading`; one line, no security implication either way (bound param already prevents injection regardless).

**CAPI-7 (risky).** Duplication confirmed: `GRAPH_REL_TYPES` (`get-neighborhood.ts:19-23`) and `RELATIONSHIP_TYPES` (`slug-map.ts:164-172`) are independent literal arrays with real semantic overlap and no compile-time link — a genuine future-drift risk, correctly flagged. But the suggested remedy (derive `GRAPH_REL_TYPES` from `RELATIONSHIP_TYPES` filtered to "the semantic subset") would invert the plan's own security posture: every allowlist in this feature (SEC-1/2/3/8, the nodeType/relType checks in `getNeighborhood`) is deliberately fail-closed — a new relationship type added to `RELATIONSHIP_TYPES` for an unrelated feature must be *added* to `GRAPH_REL_TYPES` before it's exposed through the graph view. A filter-based derivation flips that default: anything not explicitly excluded flows through automatically, which is a worse fail-open pattern for a shared, multi-tenant Neo4j instance whose entire threat model in this plan is "don't let a new label/rel type leak across knowledge bases." The underlying observation is legitimate and worth carrying into a retro or a follow-up ticket, but the specific fix as worded should not be applied mechanically — it needs a design pass (e.g., a lint/test that fails when `RELATIONSHIP_TYPES` gains an entry absent from both `GRAPH_REL_TYPES` and an explicit "structural, excluded" list) rather than a one-line `.filter()`. Flag as risk, don't auto-apply the stated fix.
