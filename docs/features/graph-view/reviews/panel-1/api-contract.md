# Panel-1 / api-contract review — graph-view

| ID | Severity | Where | Problem (≤ 25 words) | Fix (≤ 30 words) |
|---|---|---|---|---|
| API-1 | high | `packages/scripture/src/graph/explore-graph.ts:50` vs plan item 2 | Plan hardens `getNeighborhood` against the unlabeled-`MATCH` cross-tenant leak, but `exploreGraph` — same shared Neo4j instance, live MCP tool — keeps `MATCH (n {id: $entityId})` unlabeled. | Add LM-layer label constraint to `exploreGraph` in this feature (or file a same-tier follow-up), not silently leave the known vector open in a sibling function. |
| API-2 | med | plan.md Public contract vs `explore-graph.ts`/`get-verse-connections.ts` | `found` discrimination is inconsistent package-wide: `exploreGraph` uses `entity?: GraphEntity` (optional/undefined) + `message`, `getVerseConnections` has no `found` at all, `getNeighborhood` introduces `center: X \| null` + `found`. Three shapes, three consumers. | Document the convention `getNeighborhood` establishes and note in plan that it deliberately diverges from `exploreGraph`'s older shape, so it isn't read as accidental drift. |
| API-3 | med | plan.md "Failure modes" #4 vs `apps/web/.../scripture.tsx:54-59` (`parseVerseParam`) | Depth contract clamps invalid input (`0`,`4`,`abc`→1–3) but the existing `?verse` precedent treats invalid input as *absent* (null), not coerced to a nearby valid value. Two different invalid-param philosophies in the same route. | State explicitly in plan why depth clamps instead of falling back to the default-as-absent pattern `?verse` uses, or align them. |
| API-4 | med | plan.md item 3 (`?graph=<entityId>`) | No charset/length contract for `entityId` in the URL — Person/Place/Symbol/Topic ids aren't guaranteed slug-safe (apostrophes, unicode, spaces) the way verse ids are, and depth gets a Zod bound but entityId doesn't. | Add a Zod string bound (allowed charset, max length) on `entityId` before it's used as a cache-key/param, and confirm recenter links `encodeURIComponent` it. |
| API-5 | med | plan.md item 6 + item 3 (KV key `graph:v1:<id>:<depth>:<collections-hash>`) | `collections-hash` construction is unspecified — if callers can supply the array in any order, semantically-identical collection sets produce different cache keys (needless misses/duplication). | Specify canonicalization (sort + join, or stable hash) for the collections segment in the cache-key contract before implementation. |
| API-6 | low | plan.md item 2 vs `explore-graph.ts:37-42` | `getNeighborhood(neo4j, entityId, opts)` takes a single options object; `exploreGraph(neo4j, entityId, depth = 1, relTypes?)` is positional. Package now has two calling conventions for near-identical traversal queries. | Note the divergence as intentional (options-object is the going-forward convention) so future functions don't copy the older positional style. |
| API-7 | med | plan.md item 1 / Public contract (backfill script) | `--dry-run` output shape and exit codes on partial/hard failure (Postgres or Neo4j unreachable, partial batch failure) aren't specified — only the idempotent success case (FM-9: "exits 0") is contracted. | Define exit codes (0 success, non-zero on connection/partial failure) and confirm `--dry-run` reports the same `{stamped/skipped/missing}` shape as a live run, prefixed as a would-stamp preview. |
| API-8 | low | get-neighborhood.test.ts vs plan.md Public contract | Plan's public contract section describes `{degraded:true}` and `found:false` as separate failure states but doesn't spell out the nesting (`{degraded:false, neighborhood:{found,...}}`) that the loader harness actually locks in. | Add the exact discriminated-union shape to plan.md's Public contract so it's the documented source of truth, not just implicit in the test file. |
| API-9 | low | plan.md item 6 vs get-neighborhood.test.ts (FM-6 test) | "Collections: contract only... defaulting to all-public collections" — but FM-6 test passes `collections: ['canon']` explicitly and still gets records back; the caller-side default (web loader omitting `collections` entirely) isn't asserted anywhere in either harness. | Add a loader-level assertion that omitting `?collections` still resolves to the "all-public" default set end-to-end, not just at the `getNeighborhood` unit level. |
