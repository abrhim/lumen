# Data integrity review — graph-view backfill

| ID | Severity | Where | Problem (≤ 25 words) | Fix (≤ 30 words) |
|---|---|---|---|---|
| DATA-1 | high | `backfill-neo4j-collections.mjs` join key | `(from_id,to_id,rel_type)` can't disambiguate parallel Neo4j relationships (TEACHES has zero props, no element_id persisted in PG); 2 PG rows can stamp both copies with the last-processed collection_id. | Export/store Neo4j `elementId(r)` (or ordinal) during round-trips; match on it, or fall back to `LIMIT 1`+skip with a logged "ambiguous parallel edge" count instead of blind SET. |
| DATA-2 | high | `backfill-phase-b.ts:290-296` id namespacing vs. backfill script's join | Colliding entity ids get rewritten to `{type}:{id}` (+`+`-suffixed) in Postgres; the raw Neo4j `id` only survives in `metadata.neo4j_id`. A naive `from_id`/`to_id` join against Neo4j `node.id` will silently miss every namespaced entity's edges/nodes forever. | Backfill script must strip the `{type}:` prefix / read `metadata.neo4j_id` before matching, or match via `metadata->>'neo4j_id'` fallback when direct id lookup misses. |
| DATA-3 | med | Data foundation: `lumen.edges` has one edge source | Phase A creates zero edges; every current PG edge row (incl. TSK cross-refs and other Neo4j-native writes round-tripped via `backfill-phase-b.ts`) carries `collection_id='phase-b'`. Backfilling from this source stamps genuinely distinct-provenance edges identically. | Document that collection filtering is not yet meaningfully granular for edges pre-collections-feature; don't let the graph UI imply per-source filtering it can't yet deliver. |
| DATA-4 | med | Race: `backfill-phase-b.ts` DELETE-then-INSERT vs. concurrent graph backfill read | `backfill-phase-b.ts` does `DELETE FROM lumen.edges WHERE collection_id='phase-b'` then re-inserts; a concurrent Neo4j backfill run reading mid-window sees 0/partial phase-b rows and fail-open-includes live Neo4j edges as "missing collection_id." | Take an explicit PG snapshot (`BEGIN ISOLATION LEVEL REPEATABLE READ`) for the backfill read, or document "never run concurrently with phase-b backfill" as an operational constraint. |
| DATA-5 | med | Node stamping, `entities.collection_id` nullable | `lumen.entities.collection_id` is nullable (unlike edges' NOT NULL); plan doesn't define what lands on a Neo4j node when the matched PG row's `collection_id IS NULL` — literal null property vs. skip vs. treated as unstamped. | Explicitly branch: NULL PG `collection_id` → do not SET the property (same bucket as "no PG row"), and count it in the missing/skipped tally, not silently. |
| DATA-6 | med | Direction fidelity, unspecified in plan | Plan doesn't state the Cypher match must be directed (`(a)-[r:TYPE]->(b)`), matching how `export-neo4j.mjs`/`backfill-phase-b.ts` round-tripped from/to. | DATA-7 | high | Partial failure + fail-open (Q2) interaction | Crash mid-batch leaves edges processed pre-crash possibly stamped from a PG state that a concurrent ingest later changes; re-run's idempotency check (FM-9) only proves stability of a *completed* run, not that an interrupted run converged to the same result a clean run would. | Add a `--verify` pass comparing every LM edge's Neo4j `collection_id` against a fresh PG read and reporting mismatches, not just "0 new stamps." |
| DATA-8 | low | Drift: Neo4j edges with no PG counterpart | Edges with no matching PG row (stray Phase C writes, orphaned test data, interrupted prior backfills) are fail-open included forever per Q2 — FM-9's idempotency guarantee proves stability, not completeness/convergence. | Log a stable "orphan edge" report each run (not just a count) so drift is discoverable and actionable, not just permanently absorbed. |
| DATA-9 | low | Future user collections, cross-store writes | Plan defers dual PG+Neo4j writes to the collections feature but doesn't note this backfill script is the *only* reconciliation mechanism for that future write path; no scheduled/triggered re-run is proposed. | State explicitly that `backfill-neo4j-collections.mjs` must be invoked (or scheduled) after every future PG collection write until an outbox/CDC pattern exists. |

## security.md

# Security review — graph-view (PANEL-1)

| ID | Severity | Where | Problem (≤ 25 words) | Fix (≤ 30 words) |
|---|---|---|---|---|
| SEC-1 | high | `get-neighborhood.ts` depth 2–3 traversal, modeled on `explore-graph.ts` `[*1..depth]` | Cypher pattern labels only bind path endpoints; a variable-length hop can silently route through KB_*/DS_* tenant nodes mid-path, and FM-8's disjunctive assertion (any `labels()` clause OR no bare `(x)`) doesn't prove every hop is constrained. | Require `WHERE ALL(x IN nodes(path) WHERE any(l IN labels(x) WHERE l IN $lmLabels))`; strengthen FM-8 to assert per-hop, not just endpoint, constraints. |
| SEC-2 | high | `get-neighborhood.ts` depth=1 branch vs. `explore-graph.ts:49-51` | `explore-graph.ts`'s depth=1 query (`MATCH (n {id}) OPTIONAL MATCH (n)-[r]-(connected)`) is fully unlabeled; plan cites it as reference but doesn't forbid reuse — copying it leaks any-layer neighbors. | Write depth=1 fresh with the same `{Label}` constraint as depth 2-3; add an explicit depth=1 cross-tenant harness case. |
| SEC-3 | med | Query building for `truncated.total` count | Plan doesn't state whether the total-count subquery carries the same label/collection constraints as the main return; an unconstrained `COUNT` would leak the size of other tenants' graphs via `truncated.total`. | Apply identical `{Label}` and collection constraints to the count subquery; add a harness case asserting `total` excludes non-LM nodes. |
| SEC-4 | med | `packages/neo4j-http/src/layers.ts` `validateLayerQuery` | Guard strips `[:A\|B]` relationship-type patterns before scanning for raw labels, so it gives zero defense-in-depth against unsanitized `relTypes`; the manual allowlist in `getNeighborhood` is the only backstop. | Add a client.ts-level check that rel types inside `[: ]` come from a passed allowlist, mirroring the label guard. |
| SEC-5 | med | Web loader KV key `graph:v1:<id>:<depth>:<collections-hash>` | Plan doesn't define how `collections-hash` is computed; a naive join/hash can collide across different collection sets (e.g. `['a','bc']` vs `['ab','c']`), serving one caller's cached result to another. | Hash a sorted, delimiter-safe (e.g. `sha256(JSON.stringify([...collections].sort()))`) representation in the cache key. |
| SEC-6 | med | `getNeighborhood` opts `collections?: string[]`; consumed by web + MCP (`packages/scripture` "shared by web + MCP" per plan) | No server-side check ties `collections` to the caller's `owner_id`/`public` row in Postgres `lumen.collections`; function accepts caller-asserted IDs as-is.
