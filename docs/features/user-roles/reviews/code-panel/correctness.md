| CORRECTNESS-1 | high | `apps/web/app/lib/admin-users.server.ts:184-196` (cursor `k` minted via `new Date(...).toISOString()`) | Keyset cursor loses sub-millisecond precision, violating H4's "no dupes, no skips across ties". postgres.js parses `timestamptz` into a JS `Date` (ms resolution) and `toISOString()` re-truncates, but `auth.users.created_at`/`last_sign_in_at` carry microseconds (`now()`), so the cursor `k` is strictly LESS than the boundary row's true value. Desc pages then SKIP every row tied with the boundary timestamp (batch-created users share one `now()` — exactly the tie case the `(col,id)` keyset exists for) plus any row in the boundary's same-millisecond window; asc pages RE-INCLUDE the boundary row and its ties (duplicate rows + duplicate React keys). The H4 test hides this: `makeUserRow` uses whole-day `Date`s and even pins the lossy behavior (`admin.users.test.ts:177` expects `created_at.toISOString()`). | Mint the cursor from a full-precision key: project the sort column as text in the page SELECT (e.g. `u.created_at::text AS created_at_key`) and put that string in `k` (the existing `${k}::timestamptz` bound-param compare parses it losslessly). Add an H4 tie/micros regression with `…123456+00` fixtures. |
| CORRECTNESS-2 | high | `apps/web/app/lib/admin-users.server.ts:26` (`sort in SORTS`), `:73` (`c.s in SORTS`), `:129` (`statusRaw in STATUSES`), consumed at `:148,151-164` | The allow-list membership checks use the `in` operator, which walks the prototype chain — `?sort=toString`, `?sort=valueOf`, `?status=hasOwnProperty`, `?sort=__proto__` all PASS validation. This violates D6's "sort allow-list server-side" / H3's "never into SQL" contract (request-derived lookups reach `sql.raw` position), and with `?sort=toString&cursor={s:"toString"…}` also breaches H4b's bad-cursor-never-throws (decodeCursor's `c.s in SORTS` + `c.s===sort` both pass). Not injection — the leaked strings are fixed `Object.prototype` stringifications — but the "allow-list is total" test claim is false. Blast radius is confined to post-gate (entitled) requests. | Replace all three membership checks with `Object.hasOwn(SORTS, sort)` / `Object.hasOwn(STATUSES, statusRaw)` (or a `Set` of keys). | CORRECTNESS-3 | med | `apps/web/app/routes/admin.users.tsx:160-169` (append effect deps `[fetcher.data, fetcher.state, epoch]`) | The D6 epoch race-guard fails on an epoch ROUND-TRIP. `fetcher.data` persists while the component stays mounted, so: load page 2 under epoch E → add a filter (epoch F, effect resets tail) → remove it again (back button or chip; epoch E again). The `epoch` dep re-fires the append effect, `fetched.epoch === epoch` now passes, and the RETAINED page-2 payload is silently re-appended onto the fresh page 1 — 25 unrequested rows, duplicates/skips if the data shifted since (dup React keys on `u.id`), and `extra.cursor` regresses to the stale boundary. | Make consumption once-only: keep a `useRef` of the last-applied `fetcher.data` object (or a monotonically increasing request nonce in the fetcher URL echoed by the loader) and skip the append when it already applied; the epoch check alone cannot distinguish "new page for E" from "old page for a previous E". |
